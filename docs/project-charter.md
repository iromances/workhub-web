# WorkHub 项目宪章

## 1. 项目定位

WorkHub 是一个面向内部团队的项目与工作项管理系统。第一阶段重点解决企业微信等渠道来的需求、缺陷、运维事项、临时任务无法集中登记、缺少统一跟踪、状态不透明、历史留痕不足的问题。

## 2. 业务目标

1. 建立统一收口。
来自企业微信回调、人工录入、粘贴整理的事项都进入统一待整理箱。

2. 建立统一工作项模型。
需求、缺陷、运维、任务采用统一字段体系和流转规则，避免多个台账并存。

3. 建立全生命周期跟踪。
从登记、澄清、评估、排期、开发、测试、发布到完成，全程留痕。

4. 提高整理效率。
对企微原始消息和人工粘贴文本提供 AI 结构化整理能力，但必须人工确认后入正式工作项。

5. 提高项目透明度。
通过项目、迭代、版本、工作项列表与看板，实现进度可见、责任人明确、历史可追。

6. 沉淀支付接入配置界面。
统一维护支付渠道、商户账号、生产参数、秘钥版本和项目用途绑定，避免分散在多个项目台账中。

## 3. 第一阶段范围

范围内：

- 本地账号密码登录
- 项目管理
- 迭代管理
- 版本管理
- 工作项管理
- 跟踪记录
- 状态流转日志
- 附件关联
- 企业微信入站收件箱
- 企业微信群机器人出站通知
- AI 整理草稿
- 支付渠道/商户/密钥/绑定配置页面
- 列表、筛选、详情、看板

范围外：

- 企业微信单点登录
- 复杂权限模型和组织架构同步
- 自动审批流引擎
- 自动创建正式需求且不经人工确认
- 多租户
- 工时、成本核算
- 真实支付交易下发与资金执行控制台

## 4. 统一对象模型

核心对象：

- 项目
- 迭代
- 版本
- 工作项
- 工作项跟踪记录
- 工作项状态流转日志
- 企微收件箱记录
- 附件
- 用户

工作项类型：

- 需求
- 缺陷
- 运维
- 任务

规则：

- 每个工作项必须归属一个项目。
- 运维事项也必须归属项目，默认通过“公共运维项目”或具体业务项目承载。
- 每个工作项至少包含创建人、负责人、跟进人。
- AI 只能生成草稿，不能跳过人工确认直接入正式台账。

## 5. 生命周期基线

标准状态：

`待整理 -> 待澄清 -> 待评估 -> 待排期 -> 开发中 -> 测试中 -> 待发布 -> 已完成`

补充终态：

- 已拒绝
- 已挂起

状态使用原则：

- `待整理` 只用于收件箱和待转化草稿，不用于正式已确认工作项。
- 正式工作项从 `待澄清` 开始流转。
- 任何状态变更都必须生成流转日志。
- 关闭类状态必须填写结论说明。

需求管理侧补充生命周期：

- 识别前状态不进入需求业务生命周期，只通过 `enrichmentStatus` 展示系统处理进度。
- 识别成功后，`研发需求` 进入完整业务生命周期：
  `已收录 -> 待澄清 -> 待评估 -> 待排期 -> 待设计 -> 开发中 -> 测试中 -> 待验收 -> 待上线 -> 已完成`
- 识别成功后，`数据提取/运维` 进入精简业务生命周期：
  `已收录 -> 待澄清 -> 待处理 -> 处理中 -> 待验收 -> 已完成`
- 任一非终态需求可暂停为 `已暂停`，暂停时必须填写暂停原因和暂停日期，并保存暂停前状态；恢复时只能回到暂停前状态。
- 任一非终态需求可填写关闭原因后进入 `终止关闭`，关闭和暂停恢复均需能在修改历史中查询。

## 6. 成功标准

1. 任一来自企微或人工录入的事项都能在系统中找到源记录。
2. 任一正式工作项都能查到负责人、当前状态、所属项目、最近跟进记录。
3. 任一状态变更都能回溯操作者、时间和原因。
4. 项目维度可以看到迭代、版本、工作项分布和当前阻塞项。
5. AI 整理结果能减少人工整理时间，但不会直接污染正式数据。

## 7. 开发原则

1. 先做稳定台账，再做自动化增强。
2. 先确保留痕与追踪，再做智能推荐。
3. 前后端契约优先，避免页面先跑、接口后补。
4. 文档先行，需求扩展先更新项目宪章和实施路线。
5. 能复用统一对象模型时，不为单一场景单独造表。

## 8. 防飘逸约束

以下事项必须先更新文档再开发：

- 引入新的工作项类型
- 改变生命周期主状态
- 让 AI 直接写正式数据
- 新增审批流、权限流、组织流
- 引入新的基础设施，例如消息队列、搜索引擎、对象存储


## Agent 工作台扩展（2026-11-04，v4 已获用户批准）

WorkHub 是企业与 Agent 的桥梁。工作台中的 Agent 是配置与管理对象，实际使用系统已配置的 AI API 或原生 CLI；可创建多个 Agent，配置职责、模型、工具及业务线/环境范围，并分派立即或周期的巡检、分析、研发和其他任务。模型 API 通过受控工具完成任务，CLI 保留原生规划方式。

通用 Agent 任务独立于人工收件箱和正式工作项生命周期。授权范围内允许自主分析、形成修复分支并实际测试；测试发布及生产上线仍由人审核，WorkHub 调用现有 Jenkins，不能由 AI 自行批准。普通人工收件和需求确认规则保持适用。任务运行、AI 接入快照、工具证据、人工补充和产物必须留痕，报告不能冒充代码、测试或发布完成。

完整规格归档在后端业务线 BL000012 的 REQ-bf94e06e-8737-47dc-a7ba-68dba9556f9e，用户已确认“按 v4 开始实施”，并补充“目前复用现有 AI API 和 CLI”。

巡检问题作为独立对象展示受控监测证据、AI 分析方案和活动运行。AI 发现的问题及其时效阈值属于待核实判断；原始记录时间、观察时间、出现次数与处理版本由后端保存。分析报告或任务结束不代表故障已修复，也不直接生成正式工作项。

研发任务的候选变更清单冻结所有参与仓库、准确提交、差异、依赖顺序及 AI 提出的验收和回退方案。候选快照不等于已交付或已实测；缺少平台验证证据时明确待完成，不能进入发布审核。代码或关联问题方案变化后保留旧版本并标明失效。

候选代码可由授权 Agent 交付至管理员绑定的 GitLab 项目，保存每仓库分支和 Draft MR 的实际核验记录。未知写入只核对原请求；清单新版本不能绕过旧请求对账。远端已核验仍不等于实测通过或获得发布批准，测试及审核缺项继续显示。

整组发布审核绑定同一候选版本的全部仓库、实测证据、目标业务线/环境和 Jenkins Job 顺序。AI 可准备草案，人通过审核后由 WorkHub 自动执行既有 Job；生产阶段单独审核。证据缺失或材料变化禁止批准，驳回意见回到原任务。部署成功仍需业务效果复查。


### 2026-11-04 ZCode CLI 接入补充

AI 接入配置区分 Codex 与 GLM ZCode 的 CLI 协议。ZCode 使用已有程序、可选 Node 运行时、既有 Provider 定义和认证配置，模型/推理档位按 ZCode 实际配置填写；不会套用 Codex 模型目录或触发软件安装。Agent 工作台原生任务统一使用获授权的 WorkHub 工具，连接测试仅作最小模型请求。旧本地研发分析场景暂不提供 ZCode 选项；测试环境的 Jenkins 独立构建测试与人工发布审核分别呈现，本次不执行生产构建测试。

### 运行未知结果人工核对（T-04，实施契约）

运行详情接入独立 reconciliation 预览/提交接口，仅人具备 Agent 管理与任务操作权限时可提交。逐项展示 API、CLI 与在途工具的原调用及回执；核实全部未知调用后选择重新规划、等待补充或结束。保留核对依据，不能将人工结论当作平台实测或发布成功；仍存活的本机 CLI 不允许解除占用。提交固定版本、材料摘要和幂等键，二次确认后发送，结果未知可重试原请求；切换运行、权限撤销、停用或关闭核对区时拒绝迟到响应。具体实现和验证结果以本需求 Tasks 为准。
